## 0x00 Crypto｜打印店的取件暗号

### 题目信息

- **题目名称**：打印店的取件暗号
- **方向**：Crypto
- **分值**：500
- **附件**：`打印店的取件单.txt`（24 字节，含换行；MD5 `38340d2156e1efb65f6d9d61a5308f86`）
- **题面密文**：`h{vrfelmf1zu0_1gfip_fs}`
- **已知 flag 格式**：`flag{...}`

### 解题过程

拿到的是一个 24 节的纯 ASCII 文件，先确认没有隐藏字节：

```bash
$ cat -A 取件单.txt
h{vrfelmf1zu0_1gfip_fs}$
$ xxd 取件单.txt
00000000: 687b 7672 6665 6c6d 6631 7a75 305f 3167  h{vrfelmf1zu0_1g
00000010: 6669 705f 6673 7d0a                      fip_fs}.
```

密文 23 个字符，明文 `flag{...}` 同样长度，说明这是等长变换，没有压缩、没有编码展开。于是第一反应是按单层古典密码去试：26 位移凯撒、Atbash、Atbash+凯撒、仿射（全部 12 个可逆 a 与 26 个 b）、栅栏 2–22 栏、rot13，全部跑了一遍，**没有一个结果以 `flag{` 开头**。

单层全 miss 之后，我不再猜家族，改为从密文本身推硬约束：

1. 明文形式是 `flag{xxxx...}`，左花括号在第 4 个字符（下标 4）；密文里 `{` 在下标 1。**下标变了，说明必然存在换位（转置）操作**——任何纯替换都不会移动字符位置。
2. 明文里必有一个 `a`（`flag` 的第 3 个字符），而密文 `h{vrfelmf1zu0_1gfip_fs}` 中**根本没有 `a`**。替换可以映射 `a→其它字符`，但换位不会凭空空降一个 `a`。所以**必然还存在一层替换**。

两条约束合起来只剩一个结论：出题人叠了「换位 + 替换」两层。层数确定为 2 之后，穷举空间从"任意古典密码"塌缩为"一个换位家族 × 一个替换家族"，这就可算了。

**第一层：栅栏（3 栏）。** 栅栏加密的规则是：把明文按锯齿形写入 3 行（行号 0→1→2→1→0→…），再按行拼接成密文。n=23、k=3 时锯齿周期为 4，三行容量分别是 6 / 11 / 6。解密的做法是先把密文按容量切成三段，再按同样的锯齿路径从三段里依次取字符：

```python
import os

ct = open('/home/kali/ctfwork/5/' + os.listdir('/home/kali/ctfwork/5')[0]).read().strip()

k = 3
n = len(ct)

def rail(i, k=3):                 # 第 i 个明文字符所在的行号
    p = 2 * (k - 1)
    m = i % p
    return m if m < k else p - m

pat = [rail(i) for i in range(n)]  # 0,1,2,1,0,1,2,1,...

rails, pos = [], 0
for r in range(k):                 # 按行切分密文
    c = pat.count(r)
    rails.append(ct[pos:pos + c])
    pos += c

# 按锯齿顺序回读
plain = ''.join(rails[pat[i]][sum(1 for j in range(i) if pat[j] == pat[i])] for i in range(n))
print(plain)
```

输出：

```
hlim{fp1vz_ur0f_f1sgef}
```

`{` 已经从下标 1 回到下标 4，位置约束对上了；但字符仍然不可读（`hlim` 而不是 `flag`），正好留给第二层。

**第二层：仿射替换。** 仿射密码的加密式是 `c = (a·p + b) mod 26`，解密式是 `p = a⁻¹·(c − b) mod 26`。对 `hlim{fp1vz_ur0f_f1sgef}` 逐字符解（只处理 a–z，数字、下划线、花括号原样保留），当 `a=5, b=8`（`a⁻¹=21`）时得到：

```python
a, b = 5, 8
ai = pow(a, -1, 26)                # 21
s = ''.join(chr((ai * (ord(c) - 97 - b)) % 26 + 97) if c.islower() else c
            for c in plain)
print(s)
```

```
flag{pr1nt_sh0p_p1ckup}
```

**验证。** 单看明文不算数，必须能反向加密回原密文才算真解。仿射正向加密得到 `hlim{fp1vz_ur0f_f1sgef}`，再做 3 栏栅栏加密（锯齿写入、按行读出），逐字节比较：

```
re-encode == cipher: True
```

双向闭合，方案唯一。

### 遇到的问题

- **最大的一次误判是"先猜家族"**。单层家族我穷举得并不少（26 位移 × 全仿射 × 栅栏 2–22 × 全部列置换宽度 2–7 全排列，以及两两组合约 26×5913 次），但出题人叠了两层，再全面的单层穷举也一定全 miss。后来改走"从格式反推层数"，两分钟就定位了。
- **栅栏方向我第一次写反了**。把"按行切分"和"按锯齿回读"的顺序颠倒，得到 `hlimfp{1_vzur0f_1sfg}ef` 这种明显错位的结果。判据很简单：解密结果里 `{` 必须落在下标 4，否则就是方向错了。
- 仿射只作用于字母，**不能把数字和下划线一起参与模运算**，否则 `1`、`0`、`_` 会被算坏。

### 技术总结

这道题的考点不是某个具体算法，而是**从格式约束反推变换层数**。`{` 的位置变化证明有换位，字符集缺字证明有替换，两条硬约束把无限可能收窄到"栅栏 × 仿射"这一组合。古典密码题里，先做约束推理再枚举，比上来就堆字典高效一个数量级。

## 0x01 Misc｜迎新礼包

### 题目信息

- **题目名称**：迎新礼包
- **方向**：Misc
- **分值**：500
- **附件**：`迎新礼包.zip`（76430 字节），解压得一张 1920×1080 JPEG，128880 字节，MD5 `ec087ccfbd5a309544427aa0a54d63b8`
- **已知 flag 格式**：`flag{...}`

### 解题过程

先做常规三件事：`file` 认类型、`strings` 找明文、`exiftool` 看元数据。

```bash
$ file 590_0_e8bf8ee696b0
590_0_e8bf8ee696b0: JPEG image data, JFIF standard 1.01, aspect ratio, density 1x1,
segment length 16, Exif Standard: [TIFF image data, big-endian, direntries=5,
description=pw=K5CUYQ2PJVCS2MRQGI3A====, manufacturer=Xiaomi, model=Xiaomi 14,
software=MIUI 15, datetime=2026:09:05 09:12:33], baseline, precision 8,
1920x1080, components 3
$ strings -n 8 590_0_e8bf8ee696b0 | grep -i flag
flag.txt
flag.txt
```

`strings` 里只有 `flag.txt` 这个文件名出现两次（后来知道分别来自 ZIP 的本地文件头和中央目录），没有明文 flag，说明 flag 被包在某个容器里。紧接着 `exiftool` 给出了关键线索：

```bash
$ exiftool 590_0_e8bf8ee696b0
...
Image Description               : pw=K5CUYQ2PJVCS2MRQGI3A====
Make                            : Xiaomi
Camera Model Name               : Xiaomi 14
Software                        : MIUI 15
Modify Date                     : 2026:09:05 09:12:33
Image Width                     : 1920
Image Height                    : 1080
```

`ImageDescription` 被人改成了 `pw=...`，后面那串带 `====` 的补位像是 base64。先按 base64 解：

```bash
$ echo 'K5CUYQ2PJVCS2MRQGI3A====' | base64 -d
# 输出一堆不可打印字节，乱码
```

失败。看字符集——只含 A–Z 与 2–7，且补了 4 个 `=`，这正是 **base32** 的特征（base32 的字母表是 `A-Z2-7`，按 8 字符一组补位，最多补 6 个 `=`）：

```bash
$ echo 'K5CUYQ2PJVCS2MRQGI3A====' | base32 -d
WELCOME-2026
```

密码到手：`WELCOME-2026`。接下来找容器。这台 Kali 上的 `binwalk` 是坏的：

```bash
$ binwalk 迎新礼包.jpg
ModuleNotFoundError: No module named 'imp'
```

（Python 3.13 移除了 `imp` 模块，binwalk 的老版本仍 import 它。）于是自己写段脚本遍历 JPEG 段，找到 EOI 标记 `FFD9` 的位置，并检查其后是否还有数据：

```python
d = open('590_0_e8bf8ee696b0', 'rb').read()
i, eoi = 2, None
while i < len(d) - 1:
    if d[i] != 0xFF:
        i += 1
        continue
    m = d[i + 1]
    if m == 0xD9:                       # EOI
        eoi = i
        break
    if m in (0xD8, 0x01) or 0xD0 <= m <= 0xD7:
        i += 2
        continue
    seglen = int.from_bytes(d[i + 2:i + 4], 'big')
    i += 2 + seglen

print('EOI @', eoi, 'file size', len(d), 'tail', len(d) - (eoi + 2))
tail = d[eoi + 2:]
print('tail magic', tail[:4])
open('out.zip', 'wb').write(tail)
```

输出：

```
EOI @ 128683 file size 128880 tail 195
tail magic b'PK\x03\x04'
```

EOI 之后干净利落地跟了一个 195 字节的 ZIP 本地头。`zipinfo` 看结构：

```bash
$ zipinfo out.zip
Archive:  out.zip
Zip file size: 195 bytes, number of entries: 1
?rw-------  2.0 fat       29 Bx u099 26-Oct-20 11:37 flag.txt
1 file, 29 bytes uncompressed, 47 bytes compressed:  -62.1%
```

`u099` 表示压缩方法 99，即 **WinZip AES 加密**（`zipinfo -v` 里还能看到 extra field `0x9901`、vendor `AE`、strength `03` = AES-256）。这也解释了为什么 `unzip` 会直接失败：

```bash
$ unzip -o -P WELCOME-2026 out.zip -d ./x
Archive:  out.zip
   skipping: flag.txt                unsupported compression method 99
```

方法 99 只有 7-Zip 系工具认：

```bash
$ 7z x -pWELCOME-2026 out.zip -o./x2
...
Everything is Ok
$ cat x2/flag.txt
flag{jpg_ta1l_1s_n0t_4n_3nd}
```

### 遇到的问题

- **base64 先入为主**。`====` 补位看起来太像 base64，实际字符集 `A-Z2-7` 才是判据。以后遇到补位多的串，先看字母表再选解码器。
- **`unzip` 报 method 99 时不要以为是密码错**。密码错会明确说 `incorrect password`，报 method 99 是算法不支持，必须换 `7z x -p<pw>`。
- `binwalk` 在这台机器上不可用，段扫描改用脚本遍历 `FFxx + length`。顺便说，`foremost`/`dd` 也能切，但先找到 EOI 偏移再 `dd` 更可控。

### 技术总结

这是一道典型的"容器套娃 + 元数据外带密码"题。链路是 **JPEG（EOI 后追加 ZIP）→ EXIF 藏密码 → base32 解 → AES ZIP**。三个卡点分别考：会不会看 EOI 之后的脏数据、会不会从字符集判断编码、知不知道 method 99 要用 7z。方法论上，先 `file`/`strings`/`exiftool` 三连扫一遍，再决定往哪个方向深挖，比一上来就跑 stegsolve 高效。

## 0x02 Misc｜P图只P自己

### 题目信息

- **题目名称**：P图只P自己
- **方向**：Misc
- **分值**：500
- **附件**：`P图只P自己.zip`，解压得两张 1920×1080 PNG：`591_0_e5aebfe8888d`（47096 字节，原图）、`591_1_e5aebfe8888d`（48407 字节，精修图）
- **已知 flag 格式**：`flag{...}`

### 解题过程

两张同尺寸的图放在一起，题目又叫"P图只P自己"，意图很明确：**差异即信息**。但在动手 diff 之前，先排除元数据路线——用脚本列出 PNG 的全部 chunk：

```python
import struct
d = open('591_0_e5aebfe8888d', 'rb').read()
i = 8
while i < len(d):
    ln = struct.unpack('>I', d[i:i+4])[0]
    typ = d[i+4:i+8]
    print(typ.decode(), ln, 'offset', i)
    i += 12 + ln
```

两张图都只有 `IHDR / IDAT / IEND`，没有 `tEXt`、`iTXt`、`zTXt`，`IEND` 之后也没有尾随数据。元数据路线排除，回到像素。

接下来写一个纯标准库的 PNG 解码器（`zlib` + 五种 filter 的逆运算），把两张图解成 RGB 裸数组，逐像素求差，并把差异分成"小"（|Δ|≤4）和"大"（|Δ|>4）两类：

```python
def read_png(path):
    d = open(path, 'rb').read(); i = 8; idat = b''; w = h = ct = None
    while i < len(d):
        ln = struct.unpack('>I', d[i:i+4])[0]; typ = d[i+4:i+8]; data = d[i+8:i+8+ln]
        if typ == b'IHDR': w, h, _, ct = struct.unpack('>IIBB', data[:10])
        elif typ == b'IDAT': idat += data
        i += 12 + ln
    raw = zlib.decompress(idat)
    ch = {0: 1, 2: 3, 4: 2, 6: 4}[ct]; st = w * ch
    out = bytearray(h * st); prev = bytearray(st); p = 0
    for y in range(h):
        f = raw[p]; p += 1
        line = bytearray(raw[p:p+st]); p += st
        if f == 1:                                   # Sub
            for x in range(ch, st): line[x] = (line[x] + line[x-ch]) & 255
        elif f == 2:                                 # Up
            for x in range(st): line[x] = (line[x] + prev[x]) & 255
        elif f == 3:                                 # Average
            for x in range(st):
                a = line[x-ch] if x >= ch else 0
                line[x] = (line[x] + ((a + prev[x]) >> 1)) & 255
        elif f == 4:                                 # Paeth
            for x in range(st):
                a = line[x-ch] if x >= ch else 0; b = prev[x]
                c = prev[x-ch] if x >= ch else 0
                pp = a + b - c
                pa, pb, pc = abs(pp-a), abs(pp-b), abs(pp-c)
                pr = a if (pa <= pb and pa <= pc) else (b if pb <= pc else c)
                line[x] = (line[x] + pr) & 255
        out[y*st:(y+1)*st] = line; prev = line
    return w, h, ch, out

w, h, ch, A = read_png('591_0_e5aebfe8888d')
_, _, _, B = read_png('591_1_e5aebfe8888d')
st = w * ch
big, small = [], []
for y in range(h):
    for x in range(w):
        o = y*st + x*ch
        d = [B[o+k] - A[o+k] for k in range(ch)]
        if max(abs(v) for v in d):
            (big if max(abs(v) for v in d) > 4 else small).append((x, y, *d))
print('total', len(big) + len(small), 'big', len(big), 'small', len(small))
```

第一层结论非常干净：

```
total 227 big 27 small 200
small channels Counter({(True, False, False): 200})     # 全部只在 R 通道
small abs values Counter({1: 200})                      # 全部 |Δ| = 1
big channel mask Counter({(False, False, True): 27})     # 全部只在 B 通道
```

也就是说，200 个"小差异"全在 **R（红）通道**、幅度恰好 ±1——这是典型的诱饵层，模拟"图片被重新压缩/重采样"时的抖动噪声，专门用来干扰 `compare` 类工具的肉眼判断。真正的信息是 **B（蓝）通道** 上的 27 个点。

第二层：这 27 个点的 Δ 不是图像内容，而是**数值**。把 `Δ = 精修图 − 原图`（B 通道）按 **(y, x) 行优先**排序，直接取 ASCII：

```python
big.sort(key=lambda r: (r[1], r[0]))          # 行优先
print([r[4] for r in big])                     # B 通道差值
print(''.join(chr(r[4]) for r in big))
```

输出：

```
[102, 108, 97, 103, 123, 112, 104, 48, 116, 48, 115, 104, 48, 112,
 95, 48, 110, 108, 121, 95, 109, 121, 53, 51, 108, 102, 125]
flag{ph0t0sh0p_0nly_my53lf}
```

27 个 diffs 正好对应 27 个字符串——`flag{` + 20 个字符 + `}`。

### 遇到的问题

- **排序方向是这道题真正的坑**。同一组 27 个数值，按 `(x, y)` 列优先排出来是 `fhpmg0ysft__30hl{pya00l5ln}`，看起来同样是"乱码但像 flag"，很容易误判成还差一层解密。按 `(y, x)` 行优先才是完整可读的 flag。判据：行优先结果以 `flag{` 开头且以 `}` 结尾，唯一自洽。
- **阈值不能当二值图看**。第一版脚本用 `m > 6` 判定差异，得到 27 个点，但把它们画成二值 PNG 后什么也读不出——因为信息不在"点的位置构成的图案"里，而在"点的数值"里。把 Δ 当字符码，而不是当像素，才是正解。
- PNG 解码必须实现全部五种 filter。只处理 `None` 的话，第一行之后全是错的，diff 结果会是一团噪声。

### 技术总结

考点是**差异的两层分离**：先按通道和幅度把"诱饵噪声"和"真实信息"分开（R 通道 ±1 vs B 通道大值），再按正确的遍历顺序把数值还原成字符。这类题的关键判据永远是"结果能不能自我解释"——`flag{...}` 的首尾配对、长度对齐，比任何工具输出的"看起来像"都可靠。

## 0x03 Reverse｜打印店的价目表

### 题目信息

- **题目名称**：打印店的价目表
- **方向**：Reverse
- **分值**：500
- **附件**：`打印店的价目表.exe`（44544 字节，PE32+ console，x86-64，9 节，stripped to external PDB；MD5 `9e30d00a3e0afc606f15710d53b8b354`）
- **已知 flag 格式**：`flag{...}`

### 解题过程

先做 PE 静态三件套：`file`、`strings`、导入表。`file` 确认是 64 位控制台程序；`strings -n 6` 直接就有收获：

```bash
$ strings -n 6 打印店的价目表.exe | grep -n -E 'flag\{pr1nt|_sh0p_|m3mb3r|_pr1c3'
62:flag{pr1nt
63:_sh0p_
64:m3mb3r
65:_pr1c3}
```

四段被 `\0` 分隔的字符串，拼起来正好是 `flag{pr1nt_sh0p_m3mb3r_pr1c3}`。**但不能直接提交** —— 这类题常见的陷阱是把诱饵串摆在 `.rdata` 里，真校验走的是另一条路径。必须找到引用它们的代码，确认拼接顺序和长度校验。

四段中间都是 `\0`，用字节搜索确认它们连续存放：

```bash
$ python3 -c "d=open('打印店的价目表.exe','rb').read(); i=d.find(b'flag{'); print(hex(i), repr(d[i:i+34]))"
0x8600 b'flag{pr1nt\x00_sh0p_\x00m3mb3r\x00_pr1c3}'
```

文件偏移 `0x8600` 对应虚拟地址 `0x14000a000`（映像基址 `0x140000000` + `.rdata` RVA `0xa000`）。校验函数在 `0x140001490`，它开头的 `lea` 就指向这块数据：

```asm
0x14000149c   lea  rax, str.flagpr1nt      ; 0x14000a000 ; "flag{pr1nt"
0x1400014a3   mov  qword [rbp - 8], rax    ; p = 段首
0x1400014a7   mov  qword [rbp - 0x10], 0   ; off = 0
0x1400014af   mov  rax, qword [rbp - 8]
0x1400014b3   mov  rcx, rax
0x1400014b6   call 0x140008db0              ; strlen(p)
0x1400014bb   mov  qword [rbp - 0x18], rax ; len = strlen(p)
0x1400014bf   mov  rdx, qword [rbp + 0x10] ; rdx = 用户输入
0x1400014c3   mov  rax, qword [rbp - 0x10]
0x1400014c7   lea  rcx, [rdx + rax]         ; rcx = input + off
0x1400014d6   mov  rdx, rax
0x1400014d9   call 0x140008db8              ; strncmp(p, input + off, len)
0x1400014de   test eax, eax
0x1400014e0   je   0x1400014e9
0x1400014e2   mov  eax, 0                    ; 不等 → 返回 0（失败）
0x1400014ed   add  qword [rbp - 0x10], rax  ; off += len
0x1400014f5   add  rax, 1
0x1400014f9   add  qword [rbp - 8], rax      ; p += len + 1（跳过 NUL）
0x140001501   movzx eax, byte [rax]
0x140001506   je   0x14000150a               ; *p == 0 → 段读完
```

收尾处还有一道长度闸门：

```asm
0x14000150b   mov  rdx, qword [rbp + 0x10]   ; input
0x140001513   add  rax, rdx
0x140001516   movzx eax, byte [rax]
0x140001519   test al, al
0x14000151b   sete al                        ; 要求 input[off] == '\0'
```

逻辑完整还原成 C：

```c
int check(const char *input) {
    const char *p = "flag{pr1nt\0_sh0p_\0m3mb3r\0_pr1c3}";
    size_t off = 0;
    while (*p) {
        size_t len = strlen(p);
        if (strncmp(p, input + off, len) != 0) return 0;
        off += len;
        p += len + 1;            // 跳过段间 NUL
    }
    return input[off] == '\0';   // 必须正好结束，不能多字符
}
```

这个实现决定了三条硬性要求：段序固定（`flag{pr1nt` → `_sh0p_` → `m3mb3r` → `_pr1c3}`）、段间无分隔符、总长必须精确等于 26。所以 `.rdata` 里的四段不是诱饵，而是"分段存储"的同一串——出题人用 NUL 把 flag 切成四块，逼你去读代码而不是只 `strings`。

**动态验证。** 用 wine 跑两遍，正确串和缺字符的串：

```bash
$ wine 打印店的价目表.exe 'flag{pr1nt_sh0p_m3mb3r_pr1c3}'
会员码输对了，按内部价。
老板抬头看了你一眼：内部价，一毛五。

$ wine 打印店的价目表.exe 'flag{pr1nt_sh0p_m3mb3r}'
老板：这个码不对，按普通价算。
```

正向通过、负向拒绝，逻辑闭合。

### 遇到的问题

- **差点被 `strings` 骗过去**：四段字符串直接拼接就得到 flag，看起来根本不用逆向。但这类"看起来太容易"的题必须验证——如果 `.rdata` 里那段是诱饵，直接提交就是 0 分。多花三分钟看引用它的函数，是必要成本。
- **`.rdata` 的 VA 与文件偏移不是一回事**。`0x8600` 是文件偏移，`0x14000a000` 是 VA，中间差的是映像基址和节的对齐。算错就会去错位置读数据，看到一堆无关字节。
- 收尾的 `input[off] == '\0'` 很容易漏看，导致误以为"多打几个字符也能过"。实际必须精确等长。

### 技术总结

PE 逆向的基本功：`strings` 找到候选，交叉引用（xRef）找到唯一使用点，再读校验逻辑确认"分段拼接 + 精确长度"这两个约束。判断诱饵与真校验的分水岭，永远是"有没有代码真的引用它"。

## 0x04 Reverse｜广播站的歌单

### 题目信息

- **题目名称**：广播站的歌单
- **方向**：Reverse
- **分值**：500
- **附件**：`广播站的歌单.exe`（44544 字节，PE32+ console，x86-64，9 节；MD5 `8dafc3d65eb15f9f49601fdb85677dfd`）
- **已知 flag 格式**：`flag{...}`

### 解题过程

同样是 64 位控制台程序。`strings` 一上来就给了一条很显眼的常量：

```bash
$ strings -n 20 广播站的歌单.exe | grep -E '^[A-Za-z0-9+/=]{20,}$'
========================================
ZmxhZ3tyNGQxMF9wbDR5bDFzdF9uMWdodH0=
ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/
```

第二行就是常量，第三行是 base64 的索引表——这张表的存在直接说明程序自己实现了编码，而不是调用库函数。

纯 base64 字母表、长度 36、末尾一个 `=`。直接解：

```bash
$ echo 'ZmxhZ3tyNGQxMF9wbDR5bDFzdF9uMWdodH0=' | base64 -d
flag{r4d10_pl4yl1st_n1ght}
```

得到明文。**但同样不能只停在这里**——需要确认程序真的是"把输入 base64 后与常量比较"，而不是把 flag 明文摆在 `.rdata` 里当诱饵。

用 r2 看这个常量的位置和引用：

```
[0x14000a160]> izz~ZmxhZ3ty
550  0x00008760 0x14000a160 36 37 .rdata ascii ZmxhZ3tyNGQxMF9wbDR5bDFzdF9uMWdodH0=
```

常量位于 `.rdata` 的 `0x14000a160`（文件偏移 `0x8760`），36 字节。程序的校验流程是：

1. 取 `argv[1]` 作为"点歌码"；
2. 对输入做 **base64 编码**（内联实现，不是调用库）；
3. 把编码结果与 `0x14000a160` 处的 36 字节常量做逐字节比较；
4. 全等则输出"点歌码输对了"，否则输出"码不对"。

这里有个细节值得说清：比较的是 **36 字节的 base64 串**，而 36 个 base64 字符恰好编码 26 字节原始数据（`ceil(26/3)*4 = 36`，尾部补一个 `=`）。程序里**没有**显式的长度闸门——实测 1、4、5、200 字节的输入都能跑到判定分支，只是编码结果长度对不上 36，`strncmp` 自然不等。换句话说，长度约束是"编码后比较"这个结构自带的，不是单独写的 `if`。

由于比较对象是"输入编码后的结果"，**要恢复的是原始输入**，所以正确方向是 base64 **解码**常量，而不是编码。这一步方向和 007 那种"编码后比对"正好相反，做题时必须看清比较的两边谁是输入、谁是常量。

**动态验证：**

```bash
$ wine 广播站的歌单.exe 'flag{r4d10_pl4yl1st_n1ght}'
========================================
        校园广播站 · 深夜点歌台
========================================
导播：点歌码输对了，今晚最后一首就放你点的。

导播把歌单往桌上一拍：行，最后一首给你留着。

$ wine 广播站的歌单.exe 'wrong'
========================================
        校园广播站 · 深夜点歌台
========================================
导播：点歌码输对了，今晚最后一首就放你点的。

导播头也不抬：码不对，明天再来。
```

注意这里有个迷惑设计：`导播：点歌码输对了，今晚最后一首就放你点的。` 这一行**无论输入对错都会打印**，真正的判定在最后一行。第一版我用 `tail -3` 取输出，正好被这行稳定出现的文案骗了一次，误以为"输什么都对"。动态验证时必须看最后一行，或者干脆比较两次输出的差异部分。

### 遇到的问题

- **方向和 007 类题容易混**。有的程序是"输入的 base64 == 常量"，有的程序是"输入的明文 == base64 解码后的常量"，两边看起来都是"有个 base64 常量"。判据：看比较指令的两个操作数，哪一边是 `argv` 派生出来的。
- 内联 base64 实现（没有查表而是移位拼装）在反汇编里不好认，容易误判成某种自定义编码。识别特征是出现 `>> 2`、`& 0x3f`、`<< 4` 这类位运算和 `A-Za-z0-9+/` 的索引表。
- 常量长度 36 而明文 26，中间差的是补位。误把长度当明文长度会算错。

### 技术总结

本题是"逆向 + 编码"的合流：先用 `strings` 抓到高熵候选，用 r2 确认它在 `.rdata` 且被校验函数引用，再根据比较方向决定是编码还是解码。真正需要逆向的只有"程序对输入做了什么变换"这一句，剩下的都是编码基本功。

## 0x05 Reverse｜实验楼的旧终端

### 题目信息

- **题目名称**：实验楼的旧终端
- **方向**：Reverse
- **分值**：500
- **附件**：`实验楼的旧终端`（698648 字节，ELF 64-bit x86-64，statically linked，stripped；MD5 `8eb424e444e27c962179f3bf6882b57f`）
- **已知 flag 格式**：`flag{...}`

### 解题过程

698 KB 的静态链接 ELF，符号表被剥了，`objdump -d` 几十万行没法直接读。这类题的策略是**从字符串和系统调用反推入口**，而不是从 `_start` 顺着往下读。

先找交互文案，定位错误分支。注意 `strings` 默认只输出可打印 ASCII，中文提示串是 UTF-8 字节，`strings` 抓不到，要直接在字节流里搜：

```bash
$ python3 -c "d=open('实验楼的旧终端','rb').read(); print(hex(d.find('访问码错误'.encode())))"
0x7b0c5
```

文件偏移 `0x7b0c5` 换成 VA 是 `0x47b0c5`，这条提示的字符串起始在 `0x47b0b0`（`lea` 里指向的地址）。在 r2 里对它做交叉引用，一次就落到校验分支：

```
[0x0047b0b0]> axt
(nofunc) 0x401828 [DATA] lea rdi, [0x0047b0b0]
```

同一次分析里，对数据段那两个 blob 也做 xRef，得到 `0x4017c6`（table）和 `0x4017bf`（key）。三个引用点都落在 `0x4017b0` 附近 —— 校验函数就在这里。

`0x401828` 位于一段紧邻的代码里。往前退到 `0x4017b4`，整段校验逻辑就完整了：

```asm
0x004017ac   mov  rdi, rbx
0x004017af   call 0x4010c0              ; strlen(input)
0x004017b4   cmp  rax, 0x16              ; 22
0x004017b8   jne  0x401828              ; 长度不符 → 直接报错

0x004017ba   mov  rcx, rbx              ; rcx = input
0x004017bd   xor  eax, eax              ; i = 0
0x004017bf   lea  r8, [0x00480bb6]      ; key   = 0x480bb6
0x004017c6   lea  rdi, [0x00480ba0]     ; table = 0x480ba0
0x004017cd   jmp  0x401812

0x00401812   mov  rdx, rax
0x00401815   and  edx, 3                ; i & 3
0x00401818   movzx edx, byte [r8 + rdx] ; key[i & 3]
0x0040181d   movzx esi, byte [rdi + rax] ; table[i]
0x00401821   xor  dl, byte [rcx]        ; key[i&3] ^ input[i]
0x00401823   cmp  dl, sil               ; == table[i] ?
0x00401826   je   0x401800
0x00401828   lea  rdi, [0x0047b0b0]     ; 错误串
```

还原成 C：

```c
if (strlen(input) != 0x16) return fail();     // 必须 22 字节
for (size_t i = 0; i < 0x16; i++)
    if ((input[i] ^ key[i & 3]) != table[i]) return fail();
return ok();
```

两条约束：**长度恰好 22**，以及**逐字节异或**（密钥 4 字节循环）。接下来把 key 和 table 从数据段读出来。两个地址都在 `.data` 里，按 VA − 0x400000 换算成文件偏移（静态 PIE 关闭的 ELF，段偏移恰好是这个关系）：

```python
d = open('实验楼的旧终端', 'rb').read()
off = 0x480ba0 - 0x400000
blob = d[off:off + 0x16]              # table，22 字节
key  = d[off + 0x16:off + 0x16 + 4]   # key，紧跟其后 4 字节
print(blob.hex())
print(key.hex())
```

输出：

```
3c7fa649217ff34c0567f45c3722a91a364cbf1e286e
5a13c72e
```

异或式可逆，直接解：

```python
flag = bytes(blob[i] ^ key[i & 3] for i in range(0x16))
print(flag)
```

```
b'flag{l4b_t3rm1n4l_x0r}'
```

长度正好 22，与 `cmp rax, 0x16` 对上。

**动态验证（正向 + 边界）：**

```bash
$ ./实验楼的旧终端 'flag{l4b_t3rm1n4l_x0r}'
屏幕上的字符像被什么搅过，只剩下登录框还亮着。
终端闪了一下：访问码正确，日志目录已解锁。

$ ./实验楼的旧终端 'flag{l4b_t3rm1n4l_x0}'      # 21 字节
终端响了一声：访问码错误。
```

再把长度改到 23 也是拒绝，说明 `0x16` 是精确闸门，不是"至少"。

### 遇到的问题

- **不要在静态大二进制里从 `_start` 顺着读**。698 KB、stripped，入口是 libc 的启动代码，顺着走会在初始化里耗掉大量时间。正确入口是"错误字符串 → xRef → 校验函数"，两步就到位。
- **`key[i & 3]` 的索引**容易误读成 `key[i % 4]` 之外的形式，或者误以为每 4 字节换一次密钥。反汇编里是 `and edx, 3` 再 `movzx`，确实是 4 字节循环。
- **data 段的 VA 到文件偏移换算**不能想当然。这里的 ELF 是非 PIE、静态链接，`.data` 的 VA 减 0x400000 恰好等于文件偏移；如果换成 PIE 或加了对齐，就要按节头 `p_vaddr / p_offset` 算。
- 长度校验在循环之前，先卡 `strlen`，所以输入 21 或 23 字节时根本不会进异或循环，报错信息相同。调试时别误以为是"异或算错了"。

### 技术总结

静态大二进制的标准打法：**字符串定分支，xRef 定函数，数据段取常量，最后用式子反推**。这道题的三要素是"长度 22 + 4 字节循环密钥 + 逐字节异或"，每个要素都能从四五条指令里直接读出来，不需要完整的反编译。异或类题目还有个通用检查：解出来的字节串必须全部可打印且首尾是 `flag{`/`}`，否则就是 key 或索引读错了。

## 附录 C：踩坑记录

1. **`binwalk` 在 Python 3.13 下不可用**：`ModuleNotFoundError: No module named 'imp'`。段扫描改为脚本遍历 `FFxx + length`。
2. **`unzip` 遇到 method 99**：WinZip AES 加密，`unzip` 直接报 `unsupported compression method 99`，必须 `7z x -p<pw>`。密码错与算法不支持是两种不同报错，别混。
3. **base64 与 base32 的补位都长 `=`**：判据是字母表。`A-Z2-7` 是 base32，`A-Za-z0-9+/` 才是 base64。
4. **PNG 差分必须实现全部五种 filter**：只处理 `None` 会让第一行之后全部错位。
5. **差异的"排序方向"是隐藏考点**：同一组数值按 `(x,y)` 和 `(y,x)` 排出两种结果，只有一种能自洽成 `flag{...}`。
6. **静态大 ELF 不要从 `_start` 读**：从错误字符串 xRef 进校验函数，成本低一个数量级。
7. **VA 与文件偏移**：PE 的 `.rdata` 要减去映像基址；非 PIE ELF 的 `.data` 通常 VA−0x400000；PIE 则按节头算。算错就是读到无关字节。
